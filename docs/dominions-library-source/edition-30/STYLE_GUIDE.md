# Dominions 6 Knowledge Library - House Style

This guide governs the reader-facing books from Progress Edition 24 onward. It changes the voice, not the evidence.

## The voice

The library should sound like a knowledgeable player explaining the game carefully to other players. The writing is direct, practical and easy to follow without becoming casual or vague. It can be polished, but it should not sound like a report written for a committee.

- Lead with the rule, problem or useful conclusion.
- Explain why it matters after the reader knows what it is.
- Prefer ordinary words and concrete game objects over abstract labels.
- Use `we`, `players`, `a nation`, `an army`, or the named unit and mechanic where a subject is needed. Avoid repeatedly addressing the reader as `you`.
- Use first-person wording only where it reflects an editorial decision or a shared line of reasoning. Do not force it into rules text.
- Keep contractions when they make ordinary prose sound natural, but do not imitate typing mistakes, missing punctuation or chat shorthand.
- Let short sentences carry important rules. Use longer sentences only when the relationship between several facts needs to stay together.

## Phrasing to avoid

The following constructions are not banned, but repeated use makes the library sound formulaic:

- announcing what a chapter is about instead of beginning the explanation;
- `not merely`, `not simply`, `not just`, and repeated `not X but Y` contrasts;
- repeated `rather than`, `therefore`, `however`, `in practice`, or `at this point` transitions;
- `it is important to note`, `it is worth noting`, `the key takeaway`, `crucially`, `fundamentally`, `robust`, `holistic`, or similar stock emphasis;
- strings of three abstract nouns where a concrete example would be clearer;
- polished conclusions that repeat the paragraph without adding a decision;
- symmetrical lists created only to make the prose sound complete;
- calling every interaction a `system`, `framework`, `layer`, `model`, `discipline`, or `architecture` when the game term will do.

## Structure

- Headings should name the subject plainly.
- Introductory paragraphs should tell players what the section is useful for. They should not advertise the quality or completeness of the book.
- Tables carry exact comparisons. The prose around a table should explain how to use it, not repeat every cell.
- Examples should use believable Dominions situations and make their assumptions clear.
- A section may end once the practical point is settled. It does not need a formal concluding sentence.
- Cross-references should send the reader to the canonical explanation instead of reproducing it.

## Evidence that must survive every rewrite

The following content is locked unless later research changes it:

- ruleset and mod-version labels;
- evidence labels and their distinctions;
- dates, patch numbers, hashes, identifiers, file names and load order;
- exact values, formulas, ranges, dice notation and worked arithmetic;
- source attributions, links, citations and manual locations;
- the difference between fact, derived consequence, strategic advice and an unresolved question;
- qualifications such as `approximately`, `candidate`, `observed`, `current community reference`, `queued`, `in progress`, and `not reproduced`;
- historical wording needed to interpret an older ruleset, save or scenario;
- table structure, code blocks, commands and stable anchors.

## Editing test

Every rewritten passage should pass five questions:

1. Does it still make the same factual claim?
2. Is the strength of that claim unchanged?
3. Are all conditions, exceptions and version limits still present?
4. Would a new player understand it on the first read?
5. Would an experienced player find the useful detail without digging through filler?

If a cleaner sentence would weaken a qualification or blur a source boundary, the qualification stays.
